# Working on Playlist Survivors

Playlist Survivors is a horde survivor rhythm game. It is a free, open source, non-commercial project.

We rely heavily on prototyping, and move quickly. Code and documentation get out of date fast. Ask clarifying questions at the start of sessions if you're not sure what's still current.

Vision: Playlist Survivors is "the game that doesn't need a trailer". This is because *every moment of gameplay is cinematic*. The aesthetic experience is prioritized over everything.

## Enact

`enact` below means `python3 ~/enact/scripts/enact.py`.

- **Every change goes through a worktree and CI**, whether it is made by a human, an ad hoc agent session or an Enact run. Deliver it without asking:
  1. From the main checkout, `enact worktree create <short-name>`. Work only in the printed path; never edit or commit in the main checkout.
  2. Commit there, using Conventional Commits syntax.
  3. Run `enact push` in the worktree. It rebases onto `origin/staging` (merging `master` if someone bypassed staging), runs the fast check (`scripts/check-fast`), pushes to `staging`, starts slow CI (`scripts/ci-full`) in the background and removes the worktree. On exit code 2, fix the reported conflict or failing check in the same worktree and run it again. The change is landed once it is on `staging`; nobody waits for slow CI.
- Never commit to, or push directly to, `master` or `staging`. `master` advances only when slow CI passes on `staging`; a slow-CI failure files a P0 Steward bead. `enact ci --status` shows the runner and its log. Enact fast-forwards local `staging` and `master` to match the remote, so keep the main checkout clean.
- The fast and slow check commands are in `.enact.toml`.
- Beads live in this repository (`bd`, prefix `ps`); publish bead changes with `enact sync`. Work before Enact (the native app epic `hv-t8o8`, the survivors run epic `hv-n7fn`) stays in Hive's store at `~/brain/.beads` (`hbd`); the `hv-*` ids below cite it.
- Work can run unattended with Enact (`/enact <bead|plan|task>`); most work does not go through it.
- Enact roles in use: all (Executor, Warden, Steward, Mason, Sage, Archivist). The review policy is under **Review** below.

## Features

- **Worktrees.** Use a fresh worktree per prompt or bead. Enact's hooks (`scripts/enact-worktree`) APFS-clone a seed Cargo target into its `native/target`, so its first build compiles only the workspace's crates, and move its target back into the seed on removal. Run `npm ci` in a new worktree only before touching the asset baker (`tools/baker`, `assets-src/`, `public/assets/`).
- **Validation.** Staged, cheapest first:
  1. While iterating and while fixing review findings, focused checks: `cargo test -p <crate> <filter>` for native crates, `uv run --directory tools/analysis pytest -q <tests>` for the analysis tool, `npm run check` for the baker.
  2. `scripts/check-fast`, which `enact push` runs on the rebased tree; run it yourself first only when you want the answer sooner. It is diff-aware against where the branch left `origin/staging` (the baker's lint, typecheck and asset check when its paths changed; ruff and the matching test modules for the analysis tool; `native/scripts/check-fast` for native changes; the vendor guard always) and its budget is 60 s. Set `CHANGES_BASE=<rev>` to diff against another base.
  3. Only when a change touches CI scripts, `.enact.toml`, workspace-wide configuration or shared test infrastructure: `scripts/ci-full` locally too.
  4. Slow CI, `scripts/ci-full` (every section: baker, analysis, native, survivors, survivors-replay, demo3d), runs asynchronously on the newest `staging` tip in a fresh worktree, with a persistent `CARGO_TARGET_DIR`. A pass moves `master`. Nobody waits for it. `scripts/ci` is an alias of `scripts/ci-full`; `scripts/ci-full <section>` runs one section.
- **Slow-CI failures.** A red slow-CI run files a P0 Steward bead and is fixed forward by a follow-up commit, never a revert or a rerun until it passes. It preempts all other ready work.
- **Tool failures.** Never work around a broken tool silently. When Enact, Beads, cargo, uv, a flaky test or a check script fails in a way that is not the bead's own bug, file a bead at once with the label `tooling` (under the epic of the work in flight), giving the exact command, its output and how often it has happened, or add a note to the open bead for the same failure. Continue your own bead if you can, or make the tooling bead its prerequisite if you can't. Defects in Enact are fixed at their cause, in its own repository.
- **Measurements** (native app epic). A bead's measurements, tables and raw outputs go in `native/evidence/<plan-key>/` (lowercase, as `es/` and `ts-freeze/`), linked from a short summary in the bead's own section of docs/design/native-app.md. Never append a new section to the end of the design or its appendix: parallel beads collide there. `scripts/check-fast` fails on conflict markers a rebase leaves.
- **Introspection is paused** (native app epic `hv-t8o8`, since 2026-10-24). Beads write no friction record, and nobody acts on `scripts/friction`'s triggers or due cadence retrospectives or files `introspection` or `retrospective` beads; R5 (`hv-t8o8.41`) closes the epic. The ledger, `scripts/friction` and `native/evidence/introspection.jsonl` stay as they are (docs/design/native-app.md, Introspection).
- **Long local batch jobs** (exports, corpus sweeps, oracle replays) run below the fast and slow checks: the analysis tool's corpus commands call `run_as_batch()` (`ps_analysis/batch.py`), and a native batch command does the same (re-exec under `taskpolicy -b`, or `setpriority(PRIO_DARWIN_PROCESS, 0, PRIO_DARWIN_BG)`); `nice` doesn't help on macOS (hv-t8o8.55). Slow CI's corpus parity is the exception: it runs at utility QoS (`taskpolicy -c utility`), since the background class keeps to the efficiency cores and took over an hour against the step's 30 minutes (hv-t8o8.12). Before a full export or sweep, smoke-test a new assertion with `--only` on a few hard runs.
- **Choosing a bead.** Take Steward beads first, then `velocity` beads (the operator's feedback on the native app), then plan beads in their plan's order.

- **Review.** Native app beads (`hv-t8o8`) get no cold review, except G5's rollback runner. Survivors run beads (`hv-n7fn`) get one cold warden review per milestone, run by the milestone's last bead (SF10, SH11, SW7, SP5) on the commits its beads recorded in their notes, plus a per-bead review only for SF3 (the freeze's determinism) and any change to the rollback runner; the 300-line and `native/crates/sim/` triggers don't apply to them. Otherwise one cold warden review, only for a change over 300 lines of non-test, non-documentation code (additions plus deletions against its base), or one that touches the sim's determinism (`native/crates/sim/`). The reviewer is a Warden bead or a fresh read-only subagent of your own host, told to use the warden skill and not to edit files; never run `codex exec` or `claude -p` from the shell. Check each finding against the code, fix the confirmed ones (with a regression test where behavior changed), and record what was fixed or dismissed in the bead's notes. Don't run a confirmation review of the fixes.
- **Self-review before a review** (any bead that will get one). Cold reviews here found about 8 real issues each, mostly ones the implementer could have caught (hv-t8o8.46). Before requesting the review, check your own diff for:
  - **Downstream needs:** re-read the plan sections of the beads that consume this one's output (for example the stage-parity table for exported golden data), and meet or explicitly defer each need.
  - **Claims:** every number or conclusion you wrote is backed by a kept output (`native/evidence/<plan-key>/`), says what it does not show, and agrees with what earlier sections already measured.
  - **Edge cases:** for diff or path logic, renames, deletions, an unknown base and dev or optional dependencies; for measurement code, unchecked status codes and chunk boundaries.
  - **Tests against the source:** a test that only compares a tool with itself proves little; tie outputs to the real upstream (madmom, the TS oracle, the stream) where you can.
  - **Concurrency** (beads with threads or channels): workers joined on drop, their panics re-raised on the caller, and an oracle or determinism test at the parameters' non-default values (a delay above zero, a worker against inline).
  - **Record the pass:** in the bead's notes before requesting the review, list each item above as done or not applicable, with a word on how (hv-t8o8.61).
- **Native app** (`native/`, epic `hv-t8o8`, docs/design/native-app.md). A Cargo workspace of crates (`stream`, `analysis`, `audio`, `sim`, `eval`, `render`, `players`, `app`, `cli` in `native/crates/`), with the toolchain pinned in `native/rust-toolchain.toml`.
  - Focused checks are `cargo test -p <crate>` and `cargo clippy -p <crate> --all-targets -- -D warnings` from `native/`; `native/scripts/check-fast` (run by `scripts/check-fast`) covers the crates a diff touches and their dependents.
  - A bead changing the analyzer runs corpus parity on three tracks before its candidate: `cargo run --release -p cli -- analysis-parity` from `native/` (about 2 minutes; slow CI runs a fixed sample of 8 tracks, skipped while its inputs are unchanged; `--all` by hand).
  - Tests that run whole excerpts through slow stages (hindsight decodes, corpus runs, oracle sweeps) carry `#[ignore = "release: ..."]`: the fast check skips them and `scripts/ci-full native` runs them (`cargo test -- --include-ignored`); run them locally with `cargo test -p <crate> -- --ignored` when your change touches what they cover. Keep a short smoke test of the same path in the fast check, and decode or simulate a shared excerpt once per test binary (`OnceLock`) (hv-t8o8.59).
  - The pure crates (`stream`, `analysis`, `sim`, `eval`, `players`) carry `#![forbid(unsafe_code)]` and never depend, even transitively, on `audio`, `render`, `app`, objc2, winit or wgpu: `native/scripts/crates purity` checks it in the fast check. Declare an internal dependency only once code uses it, and drop one when its last use goes (`cargo machete` runs in check-fast whenever a crate changes, hv-t8o8.70).
  - Routine checks of the app run it with `--headless` (no window, no Dock icon, muted; `--seconds N` exits after N s), e.g. `cargo run --release -p app -- --file ../public/reactive/house-128/house-128.ogg --headless --seconds 30` from `native/`; stills come from `--still <png>` and timings from `--bench`. Never open the app's window during routine testing: it takes the operator's screen and focus.
  - The native app needs no dev-server port. `native/scripts/bundle` builds the signed `PlaylistSurvivors.app`; System Audio Recording needs one click from the user the first time, so record System-mode checks as pending until then, as checks that need the speakers on are pending while they are muted. Add every check pending on the operator to `native/evidence/operator-pending.md` (what they do, the command, the consuming bead), and remove its row once the consuming bead has run it.
  - **Prototype, not specification** (since 2026-10-24): the TS game at `ts-freeze` is a reference to read, not an oracle. Never add oracle tests or bit-exact arithmetic; when a deliberate change breaks one of B1–B5's oracle tests or A1–A6's stage-parity tests, delete or rewrite that test rather than bending the code back. Keep the sim deterministic (same stream and keys, same recording) and causal (never read an entry before its `knownAt`). The fixtures in `native/oracle/` are reference data, no longer frozen. Every Phase G bead keeps the app playable and writes its run command in its notes.
  - Slow CI builds into a persistent `CARGO_TARGET_DIR` under `~/Library/Caches/playlist-survivors/` (its runner is serialized by a lock); a local build and the fast check use the worktree's `native/target/`. Never point two worktrees at one `CARGO_TARGET_DIR`: cargo names a workspace crate's artifacts by its path within the workspace, so one would link the other's stale build (hv-t8o8.79).
- **Survivors run** (epic `hv-n7fn`, docs/design/survivors-run.md). The 30-minute Vampire Survivors-style run, in zen mode with Delayed listening, in `levels/survivors.yaml`. Its beads inherit the native app epic's rules above (prototype, not specification; playable after every bead with its run command in the notes; headless checks; a deterministic, causal sim; operator-pending rows) and its plan keys (`SF`, `SH`, `SW`, `SP`) name evidence directories (`native/evidence/sf1/`). VS numbers come from docs/survivors/; never commit raw extracted game data. There are no approval or playtest pauses: feel questions go to `operator-pending.md` and later `velocity` beads. Within the plan, only SW7 retunes the easy knobs (`contactDamage`, chickens, the maxed-out heal card) and the offer table, with the bots' numbers in its notes. Measurement summaries go in the bead's own subsection under the design's Bead Notes, never a new section; each bead records its commit SHA in its notes. The reactive level and legacy mode stay playable but get no new work.
- **Vendor assets never reach git.** This repository is public. The 3D tech demo uses paid packs: Synty (`~/synty`) and everything in `~/unity_assets` (Hovl Studio, Magic Pig Games, KriptoFX, the sound and music packs), and their copies on Cygnus. Never commit or push any of their files, or anything derived from them: converted meshes, baked animation or impostor textures, converted effects, generated scenes and lightmaps, edited copies of their prefabs, materials or scenes, and built apps. They live only in the gitignored `demo3d/Assets/Vendor/` and `demo3d/Assets/Baked/`. Never force-add an ignored path, and never bypass the vendor guard (`scripts/check-fast`, slow CI, and the pre-push hook that `demo3d setup` installs in the clone's shared hooks folder, on both machines). Renders of the demo (small stills in its evidence) are fine; videos stay in `captures/`. The demo's song, *Action* (NCS), is not redistributable either: its MP3 and every conversion or crop stay local (gitignored under `songs/action/` and `public/audio/action*`), and only its song map and notes are tracked.
- **3D tech demo** (`demo3d/`, docs/tech-demo-3d/, plan keys `TD0`–`TD15`, evidence in `demo3d/evidence/<key>/`). A Unity 6.6 URP prototype, not shipping code. A plain C# choreography layer decides everything, and Unity only reflects it. It was built as a standalone run on Cygnus, the operator's Windows desktop (docs/tech-demo-3d/windows.md), on the `demo3d` branch of the private relay repository, and was integrated into master on 2026-10-29 as four squashed commits (windows.md, Integration; the relay keeps the full history). Since then its changes land through Enact like any other change, with no beads: its tasks, status and notes live in docs/tech-demo-3d/plan.md. The Mac's guard reads its sync record from `~/Library/Caches/playlist-survivors/demo3d/`; rebuild it with `uv run --project demo3d/tools demo3d sync --record-only` when the vendor sources change. It also sets up, bakes, builds and plays on the Mac, for viewing (Metal, IL2CPP; docs/tech-demo-3d/mac.md); every measurement stays Cygnus's. Agents drive Unity only in batch mode, in their own worktree's project, and check the Mac's player windowless (`-batchmode -force-metal` with `--capture-stills`). Benchmark sweeps may open a 1080p window on Cygnus (an exception to the native app's windowless rule); everything else stays windowless. Reviews follow the plan: one cold review per milestone, plus one for any change to the vendor guard.
- **Timing logs.** When the operator reports how play felt (timing, presses that did nothing), read their timing logs before guessing. The app saves each listening session, its `timing.jsonl` included, to `native/logs/sessions/<unix time>/` in the main checkout (gitignored, so a worktree has none; `PS_SESSIONS` elsewhere). Summarize one with `cargo run --release -p cli -- log [<timing.jsonl>]` from `native/` (the newest if no path; `--from`/`--to` in song seconds, `--no-table` for the summary only), set its latency chain against the targets with `ps report`, and replay it with `ps replay`. F8 in the app saves the log at once.
