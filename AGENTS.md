# Working on Playlist Survivors

Implement every prompt in its own Tollgate worktree, never by committing on master. Create one with `tg worktree create <name>`, run `npm ci` in it, make the change, validate with `scripts/check-fast`, and immediately commit using Conventional Commits syntax. Then deliver it without asking: submit with `tg candidate HEAD` in the worktree, then from the main checkout run `tg approve <candidate-id> --wait`, which runs Tollgate's gate stage and promotes the candidate to `staging`. The change is landed then. Tollgate's release stage validates the newest `staging` tip afterwards and moves `release` and remote master; Tollgate owns pushes to remote master.

## Features

Executor sessions in Hive project `playlist_survivors` work from beads.

- **Delivery.** Every change, including feature beads, delivers through an independent Tollgate worktree (`tg candidate`, then `tg approve --wait`). Never commit on master or use `tg push-master`. A bead is done when its commit is on `staging`: wait for the gate stage only, never for the release stage.
- **Worktrees.** Use a fresh worktree per prompt or bead. Run `npm ci` in each new worktree before running TS checks (a native-only bead needs none). Run Tollgate waits from the main checkout, since promotion removes the clean worktree.
- **Validation.** Staged, cheapest first:
  1. While iterating and while fixing review findings, focused checks: `npm test -- <file>`, `npm run typecheck`, `npm run check:play` when play behavior changes, `cargo test -p <crate> <filter>` for native crates.
  2. Before submitting, `scripts/check-fast` once, on the final tree, and again only after a later source change. It is diff-aware (lint, typecheck and related tests for the changed TS files; ruff and the matching test modules for the analysis tool; `native/scripts/check-fast` for native changes) and its budget is 60 s. Set `CHANGES_BASE=<rev>` to diff against another base.
  3. Only when a change touches CI scripts, the Tollgate policy, workspace-wide configuration or shared test infrastructure: `scripts/ci-full` locally too.
  4. Tollgate's gate stage, `scripts/ci-gate` (about 60 s, path-gated: the TS section when TS paths changed, the analysis section when `tools/analysis/` or `songs/` changed), runs on every candidate and blocks promotion to `staging`.
  5. Tollgate's release stage, `scripts/ci-full` (steps `ci-full-ts`, `ci-full-analysis` and `ci-full-native`: every check, `check:reactive`, `check:analysis` and the native workspace's included), runs asynchronously on the newest `staging` tip. A pass moves `release` and remote master. Nobody waits for it. `scripts/ci` is an alias of `scripts/ci-full`.
- **`ci-fix` beads.** A red release run (seen in `tg release status`, `tg status` or a candidate's report) is fixed forward by a follow-up commit, never a revert or a rerun until it passes. The first session to see it searches for an open bead with the label `ci-fix` and metadata `release_step=<failing step>`, and files one under the epic of the work in flight if there is none (adding a note to the open one otherwise): keyed by the step, not the run, since every later run fails the same way until the fix lands. A `ci-fix` bead preempts all other ready work. Tollgate's `max_release_lag = 5` pauses promotion while `release` trails `staging` by more than 5 commits after a failed run; authorize the repairing candidate with `tg approve --release-fix <id> --wait`.
- **Tool failures.** Never work around a broken tool silently. When Tollgate, Hive, Beads, cargo, uv, a flaky test or a check script fails in a way that is not the bead's own bug, file a bead at once with the label `tooling` (under the epic of the work in flight), giving the exact command, its output and how often it has happened, or add a note to the open bead for the same failure. Continue your own bead if you can, or make the tooling bead its prerequisite if you can't. Defects in Tollgate or Hive are fixed at their cause, in their own repositories, under Hive's tooling-fix rule.
- **Measurements** (native app epic). A bead's measurements, tables and raw outputs go in `native/evidence/<plan-key>/` (lowercase, as `es/` and `ts-freeze/`), linked from a short summary in the bead's own section of docs/design/native-app.md. Never append a new section to the end of the design or its appendix: parallel beads collide there. `scripts/check-fast` and the gate fail on conflict markers a rebase leaves.
- **Friction ledger** (native app epic `hv-t8o8`). Every bead writes one record, `native/evidence/friction/<bead-id>.json`, **last**: after its review fixes and after any `tg update` or rebase, right before `tg candidate`, so it counts what they cost (in its own commit or with the bead's last change): `{"bead", "phase" (W, 0, 1, A–E or R), "recorded" (ISO date-time with offset), "implementMin", "localValidationS": {"fast": s, "focused": s, ...}, "gateS"?, "releaseS"?, "coldBuildS"?, "hostLoad"? (1-minute load average), "review"? ({"findings": n, "fixed": n}, required for a reviewed bead and whenever a friction entry is `review-churn`), "friction": [{"tag", "minutes", "note"}]}`, with `friction: []` when there was none. Tags come from `native/evidence/friction-tags.json`; add a tag (with its meaning) or an alias there rather than inventing one in a record. Budgets live in `native/evidence/metrics.md`. `scripts/friction validate` checks the records (the gate runs it when `native/evidence/` changes); `scripts/friction` reports fired triggers and a due cadence retrospective. Run it after writing your record.
- **Improvement beads.** When `scripts/friction` reports a trigger needing a disposition (a tag in 3 beads since the last retrospective, or a budget over 1.5 times in 3 consecutive records; it prints their host loads, and when they weren't comparable the disposition is a reason saying so), search for an open bead with the label `introspection` and metadata `trigger=<trigger>`, else file one under `hv-t8o8` with that label and key, naming its evidence (records, bead IDs, measurements) and the cause to fix. Append its disposition to `native/evidence/introspection.jsonl` (`{"trigger": "<trigger>", "bead": "<id>"}`, or `{"trigger": ..., "reason": ...}` when it won't be fixed, such as a harness problem outside the repository). A speed change shows before and after numbers and is reverted unless the metric improves by at least 10%; it never changes the oracle's expectations or the plan's decisions.
- **Retrospectives.** Phase retrospectives are plan beads. When `scripts/friction` reports a cadence retrospective due (8 records since the last retrospective), search for an open bead with the label `retrospective` and metadata `retrospective=<its key>` (it prints the key), else file one under `hv-t8o8` that blocks nothing. A retrospective runs a read-only `sage` subagent over the epic since the last one (friction records, `metrics.md`, bead notes, Tollgate's gate and release history (`scripts/friction stages`: each candidate's gate time and each release run's step times since the last retrospective, against the budgets), review dispositions, `tooling` beads, waiting time), files an improvement bead for each recurring cost no trigger covered, records a summary in the epic's notes, and appends `{"retrospective": "<bead>", "date": "YYYY-MM-DD", "covers": [<bead ids>]}` to `introspection.jsonl`.
- **Choosing a bead.** Take `ci-fix` beads first, then introspection and retrospective beads (labels `introspection`, `retrospective`), then plan beads in their plan's order.
- **Review.** One cold warden review, only for a change over 300 lines of non-test, non-documentation code (additions plus deletions against its base) or one that touches simulation determinism in `src/sim/`, the golden hashes in `tests/golden`, or the planner checks in `src/planner/checks.ts`, `play-checks.ts` and `sim-checks.ts`. The reviewer is a fresh read-only subagent of your own host, told to use the warden skill and not to edit files; never run `codex exec` or `claude -p` from the shell. Check each finding against the code, fix the confirmed ones (with a regression test where behavior changed), and record what was fixed or dismissed in the bead's notes. Don't run a confirmation review of the fixes.
- **Self-review before a review** (any bead that will get one). Cold reviews here found about 8 real issues each, mostly ones the implementer could have caught (hv-t8o8.46). Before requesting the review, check your own diff for:
  - **Downstream needs:** re-read the plan sections of the beads that consume this one's output (for example the stage-parity table for exported golden data), and meet or explicitly defer each need.
  - **Claims:** every number or conclusion you wrote is backed by a kept output (`native/evidence/<plan-key>/`), says what it does not show, and agrees with what earlier sections already measured.
  - **Edge cases:** for diff or path logic, renames, deletions, an unknown base and dev or optional dependencies; for measurement code, unchecked status codes and chunk boundaries.
  - **Tests against the source:** a test that only compares a tool with itself proves little; tie outputs to the real upstream (madmom, the TS oracle, the stream) where you can.
- **Native app** (`native/`, epic `hv-t8o8`, docs/design/native-app.md). A Cargo workspace of crates (`stream`, `analysis`, `audio`, `sim`, `eval`, `render`, `players`, `app`, `cli` in `native/crates/`), with the toolchain pinned in `native/rust-toolchain.toml`.
  - Focused checks are `cargo test -p <crate>` and `cargo clippy -p <crate> --all-targets -- -D warnings` from `native/`; `native/scripts/check-fast` (run by `scripts/check-fast`) covers the crates a diff touches and their dependents. `npm ci` is only for TS changes.
  - The pure crates (`stream`, `analysis`, `sim`, `eval`, `players`) carry `#![forbid(unsafe_code)]` and never depend, even transitively, on `audio`, `render`, `app`, objc2, winit or wgpu: `native/scripts/crates purity` checks it in the gate. Declare an internal dependency only once code uses it (`cargo machete` runs in the release stage).
  - The native app needs no dev-server port. `native/scripts/bundle` builds the signed `PlaylistSurvivors.app`; System Audio Recording needs one click from the user the first time, so record System-mode checks as pending until then, as checks that need the speakers on are pending while they are muted. Add every check pending on the operator to `native/evidence/operator-pending.md` (what they do, the command, the consuming bead), and remove its row once the consuming bead has run it.
  - The oracle's inputs (the TS fixtures in `native/oracle/`, `native/models/` and the Python streams they were made from) stay frozen until D6: regenerate them only through their own beads. The fixtures pin each track's `public/reactive/<track>/stream.json`, `content/`, `levels/reactive.yaml` and `public/assets/` by hash, so changing any of them means regenerating `native/oracle/` from `ts-freeze` (`native/oracle/README.md`).
  - Tollgate's gate and native release steps build into persistent `CARGO_TARGET_DIR`s under `~/Library/Caches/playlist-survivors/`; a local build uses the worktree's `native/target/`.
- **Ports.** Port 5199 (and preview port 5198) belongs to the operator's own testing in the main checkout: never start, stop, reuse or browse a server on it. In a worktree, `npm run dev`, `npm run preview`, Playwright and `scripts/lib/server.ts` pick that worktree's own port automatically; `npm run port` prints it. Never pass `--port` to Vite, and don't use the `demo` launch config from a worktree, since it expects port 5199.
- **Play logs.** When the operator reports how play mode felt (timing, presses that did nothing), read their timing logs before guessing. Their dev server saves them to `logs/play/<session>.json` in the main checkout (`/Users/dthurn/playlist_survivors/logs/play/`, gitignored, so a worktree has none). Summarize one with `npm run log:play -- <path>` (newest log if no path; `--from`/`--to` in song seconds, `--no-table` for the summary only). A log the operator downloaded with F8 works the same way. See `src/live/log.ts` for what it records.
