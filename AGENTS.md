# Working on Playlist Survivors

Playlist Survivors is a horde survivor rhythm game. It is a free, open source, non-commercial project.

We rely heavily on prototyping, and move quickly. Code and documentation get out of date fast. Ask clarifying questions at the start of sessions if you're not sure what's still current.

Vision: Playlist Survivors is "the game that doesn't need a trailer". This is because *every moment of gameplay is cinematic*. The aesthetic experience is prioritized over everything.

Implement every prompt in its own Tollgate worktree, never by committing on master. Create one with `tg worktree create <name>`, make the change, validate with `scripts/check-fast`, and immediately commit using Conventional Commits syntax. Then deliver it without asking: submit with `tg candidate HEAD` in the worktree, then from the main checkout run `tg approve <candidate-id> --wait`, which runs Tollgate's gate stage and promotes the candidate to `staging`. The change is landed then. Tollgate's release stage validates the newest `staging` tip afterwards and moves `release` and remote master; Tollgate owns pushes to remote master.

## Features

Executor sessions in Hive project `playlist_survivors` work from beads. Hive's beads live in `~/brain/.beads`, not this repository.

- **Delivery.** Every change, including feature beads, delivers through an independent Tollgate worktree (`tg candidate`, then `tg approve --wait`). Never commit on master or use `tg push-master`. A bead is done when its commit is on `staging`: wait for the gate stage only, never for the release stage.
- **Worktrees.** Use a fresh worktree per prompt or bead. Run `npm ci` in a new worktree only before touching the asset baker (`tools/baker`, `assets-src/`, `public/assets/`). Run Tollgate waits from the main checkout, since promotion removes the clean worktree.
- **Staging tracked Tollgate configuration.** The local `.tollgate/` exclusion protects runtime files. For edits to the already tracked policy, use `git add -u -- .tollgate/config.toml`, then stage other intended paths separately. An explicit `git add .tollgate/config.toml` can return an ignored-directory error even after updating the index; inspect `git diff --cached --name-only` before continuing. Keep runtime files ignored; do not force-add the directory or alter its exclusion to silence the warning.
- **Capacity interruptions.** On resuming after a model-service interruption, inspect the existing native claim, owned worktree, outstanding check handles and exact Tollgate candidate before launching work. Collect surviving checks and reconcile submitted candidates before starting replacements; continue the same bead and owned worktree. Keep the claim while a provider or candidate outcome is uncertain, and record the checkpoint, live handles and next action in its notes. Add a recurrence's exact host error and affected bead/handles to the matching `tooling` bead; a model-capacity error alone does not establish a game defect.
- **Validation.** Staged, cheapest first:
  1. While iterating and while fixing review findings, focused checks: `cargo test -p <crate> <filter>` for native crates, `uv run --directory tools/analysis pytest -q <tests>` for the analysis tool, `npm run check` for the baker.
  2. Before submitting, `scripts/check-fast` once, on the final tree, and again only after a later source change. It is diff-aware (the baker's lint, typecheck and asset check when its paths changed; ruff and the matching test modules for the analysis tool; `native/scripts/check-fast` for native changes) and its budget is 60 s. Set `CHANGES_BASE=<rev>` to diff against another base.
  3. Only when a change touches CI scripts, the Tollgate policy, workspace-wide configuration or shared test infrastructure: `scripts/ci-full` locally too.
  4. Tollgate's gate stage, `scripts/ci-gate` (about 60 s, path-gated: the baker section when the baker or its inputs changed, the analysis section when `tools/analysis/` or `songs/` changed), runs on every candidate and blocks promotion to `staging`.
  5. Tollgate's release stage, `scripts/ci-full` (steps `ci-full-baker`, `ci-full-analysis` and `ci-full-native`: every check, the analysis tool's tests and the native workspace's included), runs asynchronously on the newest `staging` tip. A pass moves `release` and remote master. Nobody waits for it. `scripts/ci` is an alias of `scripts/ci-full`.
- **`ci-fix` beads.** A red release run (seen in `tg release status`, `tg status` or a candidate's report) is fixed forward by a follow-up commit, never a revert or a rerun until it passes. The first session to see it searches for an open bead with the label `ci-fix` and metadata `release_step=<failing step>`, and files one under the epic of the work in flight if there is none (adding a note to the open one otherwise): keyed by the step, not the run, since every later run fails the same way until the fix lands. A `ci-fix` bead preempts all other ready work. Tollgate's `max_release_lag = 5` pauses promotion while `release` trails `staging` by more than 5 commits after a failed run; authorize the repairing candidate with `tg approve --release-fix <id> --wait`.
- **Tool failures.** Never work around a broken tool silently. When Tollgate, Hive, Beads, cargo, uv, a flaky test or a check script fails in a way that is not the bead's own bug, file a bead at once with the label `tooling` (under the epic of the work in flight), giving the exact command, its output and how often it has happened, or add a note to the open bead for the same failure. Continue your own bead if you can, or make the tooling bead its prerequisite if you can't. Defects in Tollgate or Hive are fixed at their cause, in their own repositories, under Hive's tooling-fix rule.
- **Measurements** (native app epic). A bead's measurements, tables and raw outputs go in `native/evidence/<plan-key>/` (lowercase, as `es/` and `ts-freeze/`), linked from a short summary in the bead's own section of docs/design/native-app.md. Never append a new section to the end of the design or its appendix: parallel beads collide there. `scripts/check-fast` and the gate fail on conflict markers a rebase leaves.
- **Introspection is paused** (native app epic `hv-t8o8`, since 2026-10-24). Beads write no friction record, and nobody acts on `scripts/friction`'s triggers or due cadence retrospectives or files `introspection` or `retrospective` beads; R5 (`hv-t8o8.41`) closes the epic. The ledger, `scripts/friction` and `native/evidence/introspection.jsonl` stay as they are (docs/design/native-app.md, Introspection).
- **Long local batch jobs** (exports, corpus sweeps, oracle replays) run below Tollgate's gate and release steps: the analysis tool's corpus commands call `run_as_batch()` (`ps_analysis/batch.py`), and a native batch command does the same (re-exec under `taskpolicy -b`, or `setpriority(PRIO_DARWIN_PROCESS, 0, PRIO_DARWIN_BG)`); `nice` doesn't help on macOS (hv-t8o8.55). The release stage's corpus parity is the exception: it runs at utility QoS (`taskpolicy -c utility`), since the background class keeps to the efficiency cores and took over an hour against the step's 30 minutes (hv-t8o8.12). Before a full export or sweep, smoke-test a new assertion with `--only` on a few hard runs.
- **Choosing a bead.** Take `ci-fix` beads first, then `velocity` beads (the operator's feedback on the native app), then plan beads in their plan's order.

- **Review.** Native app beads (`hv-t8o8`) get no cold review, except G5's rollback runner. Survivors run beads (`hv-n7fn`) get one cold warden review per milestone, run by the milestone's last bead (SF10, SH11, SW7, SP5) on the commits its beads recorded in their notes, plus a per-bead review only for SF3 (the freeze's determinism) and any change to the rollback runner; the 300-line and `native/crates/sim/` triggers don't apply to them. Otherwise one cold warden review, only for a change over 300 lines of non-test, non-documentation code (additions plus deletions against its base), or one that touches the sim's determinism (`native/crates/sim/`). The reviewer is a fresh read-only subagent of your own host, told to use the warden skill and not to edit files; never run `codex exec` or `claude -p` from the shell. Check each finding against the code, fix the confirmed ones (with a regression test where behavior changed), and record what was fixed or dismissed in the bead's notes. Don't run a confirmation review of the fixes.
- **Self-review before a review** (any bead that will get one). Cold reviews here found about 8 real issues each, mostly ones the implementer could have caught (hv-t8o8.46). Before requesting the review, check your own diff for:
  - **Downstream needs:** re-read the plan sections of the beads that consume this one's output (for example the stage-parity table for exported golden data), and meet or explicitly defer each need.
  - **Claims:** every number or conclusion you wrote is backed by a kept output (`native/evidence/<plan-key>/`), says what it does not show, and agrees with what earlier sections already measured.
  - **Edge cases:** for diff or path logic, renames, deletions, an unknown base and dev or optional dependencies; for measurement code, unchecked status codes and chunk boundaries.
  - **Tests against the source:** a test that only compares a tool with itself proves little; tie outputs to the real upstream (madmom, the TS oracle, the stream) where you can.
  - **Concurrency** (beads with threads or channels): workers joined on drop, their panics re-raised on the caller, and an oracle or determinism test at the parameters' non-default values (a delay above zero, a worker against inline).
  - **Record the pass:** in the bead's notes before requesting the review, list each item above as done or not applicable, with a word on how (hv-t8o8.61).
- **Native app** (`native/`, epic `hv-t8o8`, docs/design/native-app.md). A Cargo workspace of crates (`stream`, `analysis`, `audio`, `sim`, `eval`, `render`, `players`, `app`, `cli` in `native/crates/`), with the toolchain pinned in `native/rust-toolchain.toml`.
  - Focused checks are `cargo test -p <crate>` and `cargo clippy -p <crate> --all-targets -- -D warnings` from `native/`; `native/scripts/check-fast` (run by `scripts/check-fast`) covers the crates a diff touches and their dependents.
  - A bead changing the analyzer runs corpus parity on three tracks before its candidate: `cargo run --release -p cli -- analysis-parity` from `native/` (about 2 minutes; the release stage runs a fixed sample of 8 tracks, skipped while its inputs are unchanged; `--all` by hand).
  - Tests that run whole excerpts through slow stages (hindsight decodes, corpus runs, oracle sweeps) carry `#[ignore = "release: ..."]`: the gate skips them and `scripts/ci-full native` runs them (`cargo test -- --include-ignored`); run them locally with `cargo test -p <crate> -- --ignored` when your change touches what they cover. Keep a short smoke test of the same path in the gate, and decode or simulate a shared excerpt once per test binary (`OnceLock`) (hv-t8o8.59).
  - The pure crates (`stream`, `analysis`, `sim`, `eval`, `players`) carry `#![forbid(unsafe_code)]` and never depend, even transitively, on `audio`, `render`, `app`, objc2, winit or wgpu: `native/scripts/crates purity` checks it in the gate. Declare an internal dependency only once code uses it, and drop one when its last use goes (`cargo machete` runs in check-fast and the gate whenever a crate changes, hv-t8o8.70).
  - Routine checks of the app run it with `--headless` (no window, no Dock icon, muted; `--seconds N` exits after N s), e.g. `cargo run --release -p app -- --file ../public/reactive/house-128/house-128.ogg --headless --seconds 30` from `native/`; stills come from `--still <png>` and timings from `--bench`. Never open the app's window during routine testing: it takes the operator's screen and focus.
  - The native app needs no dev-server port. `native/scripts/bundle` builds the signed `PlaylistSurvivors.app`; System Audio Recording needs one click from the user the first time, so record System-mode checks as pending until then, as checks that need the speakers on are pending while they are muted. Add every check pending on the operator to `native/evidence/operator-pending.md` (what they do, the command, the consuming bead), and remove its row once the consuming bead has run it.
  - **Prototype, not specification** (since 2026-10-24): the TS game at `ts-freeze` is a reference to read, not an oracle. Never add oracle tests or bit-exact arithmetic; when a deliberate change breaks one of B1–B5's oracle tests or A1–A6's stage-parity tests, delete or rewrite that test rather than bending the code back. Keep the sim deterministic (same stream and keys, same recording) and causal (never read an entry before its `knownAt`). The fixtures in `native/oracle/` are reference data, no longer frozen. Every Phase G bead keeps the app playable and writes its run command in its notes.
  - Tollgate's gate and native release steps build into persistent `CARGO_TARGET_DIR`s under `~/Library/Caches/playlist-survivors/`; a local build uses the worktree's `native/target/`. Never point two worktrees at one `CARGO_TARGET_DIR`: cargo names a workspace crate's artifacts by its path within the workspace, so one would link the other's stale build (hv-t8o8.79).
- **Survivors run** (epic `hv-n7fn`, docs/design/survivors-run.md). The 30-minute Vampire Survivors-style run, in zen mode with Delayed listening, in `levels/survivors.yaml`. Its beads inherit the native app epic's rules above (prototype, not specification; playable after every bead with its run command in the notes; headless checks; a deterministic, causal sim; operator-pending rows) and its plan keys (`SF`, `SH`, `SW`, `SP`) name evidence directories (`native/evidence/sf1/`). VS numbers come from docs/survivors/; never commit raw extracted game data. There are no approval or playtest pauses: feel questions go to `operator-pending.md` and later `velocity` beads. Within the plan, only SW7 retunes the easy knobs (`contactDamage`, chickens, the maxed-out heal card) and the offer table, with the bots' numbers in its notes. Measurement summaries go in the bead's own subsection under the design's Bead Notes, never a new section; each bead records its commit SHA in its notes. The reactive level and legacy mode stay playable but get no new work.
- **Vendor assets never reach git.** This repository is public. The 3D tech demo uses paid packs: Synty (`~/synty`) and everything in `~/unity_assets` (Hovl Studio, Magic Pig Games, KriptoFX, the sound and music packs), and their copies on Cygnus. Never commit or push any of their files, or anything derived from them: converted meshes, baked animation or impostor textures, converted effects, generated scenes and lightmaps, edited copies of their prefabs, materials or scenes, and built apps. They live only in the gitignored `demo3d/Assets/Vendor/` and `demo3d/Assets/Baked/`. Never force-add an ignored path, and never bypass the vendor guard (`scripts/check-fast`, the gate and the release stage, and the pre-push hook that `demo3d setup` installs in the clone's shared hooks folder, on both machines). Renders of the demo (small stills in its evidence) are fine; videos stay in `captures/`. The demo's song, *Action* (NCS), is not redistributable either: its MP3 and every conversion or crop stay local (gitignored under `songs/action/` and `public/audio/action*`), and only its song map and notes are tracked.
- **3D tech demo** (`demo3d/`, docs/tech-demo-3d/, plan keys `TD0`–`TD15`, evidence in `demo3d/evidence/<key>/`). A Unity 6.6 URP prototype, not shipping code. A plain C# choreography layer decides everything, and Unity only reflects it. It was built as a standalone run on Cygnus, the operator's Windows desktop (docs/tech-demo-3d/windows.md), on the `demo3d` branch of the private relay repository, and was integrated into master on 2026-10-29 as four squashed commits (windows.md, Integration; the relay keeps the full history). Since then its changes land through Tollgate like any other change, with no beads: its tasks, status and notes live in docs/tech-demo-3d/plan.md. The Mac's guard reads its sync record from `~/Library/Caches/playlist-survivors/demo3d/`; rebuild it with `uv run --project demo3d/tools demo3d sync --record-only` when the vendor sources change. It also sets up, bakes, builds and plays on the Mac, for viewing (Metal, IL2CPP; docs/tech-demo-3d/mac.md); every measurement stays Cygnus's. Agents drive Unity only in batch mode, in their own worktree's project, and check the Mac's player windowless (`-batchmode -force-metal` with `--capture-stills`). Benchmark sweeps may open a 1080p window on Cygnus (an exception to the native app's windowless rule); everything else stays windowless. Reviews follow the plan: one cold review per milestone, plus one for any change to the vendor guard.
- **Timing logs.** When the operator reports how play felt (timing, presses that did nothing), read their timing logs before guessing. The app saves each listening session, its `timing.jsonl` included, to `native/logs/sessions/<unix time>/` in the main checkout (gitignored, so a worktree has none; `PS_SESSIONS` elsewhere). Summarize one with `cargo run --release -p cli -- log [<timing.jsonl>]` from `native/` (the newest if no path; `--from`/`--to` in song seconds, `--no-table` for the summary only), set its latency chain against the targets with `ps report`, and replay it with `ps replay`. F8 in the app saves the log at once.
